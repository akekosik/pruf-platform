# ПРУФ — документация платформы верификации инженерных навыков

**Версия документа:** 1.0 · **Версия ядра:** `pruf.engine/1` · **Статус:** рабочий прототип

---

## 0. Одна страница для тех, кто читает только первую

ПРУФ — платформа, которая доказывает, что человек **понимает код, который принёс**. Кандидат присылает решение, платформа разбирает его в AST, строит 9–15 мутаций **именно этого решения**, прогоняет тесты в изолированной песочнице и проводит 15-минутную сессию защиты. На выходе — не «зелёные тесты», а **протокол понимания**: что человек контролирует построчно, а что за него написал ассистент.

Мы **встраиваемся, а не заменяем**. Для вузовского трека ПРУФ живёт внутри Moodle: запуск из курса по LTI 1.3 Advantage, оценка возвращается в журнал через AGS, состав группы подтягивается через NRPS. Moodle остаётся системой обучения; ПРУФ закрывает дыру, которую Moodle закрыть не может — он не умеет отличить понимание от сданного задания. Вуз при этом не платит ничего: он канал и источник данных для калибровки сложности.

Платит работодатель. Не «учим студента за деньги кафедры», а «выдаём компании воспроизводимое доказательство понимания» — за деньги компании. Это и есть разворот монетизации относительно предыдущего проекта (Стапель): ядро то же, плательщик другой.

**Три свойства, которых нет у конкурентов:**

1. **Воспроизводимость.** Любой спор разбирается пересчётом того же набора мутаций по отпечатку кода. Вердикт детерминирован.
2. **Работа без интернета и без LLM.** Всё считается локально: AST, мутации, песочница, вопросы. Это единственный способ зайти на режимные предприятия.
3. **Привязка к строке.** Вопрос строится из конкретной строки конкретного решения и живёт ровно 15 минут. Обойти внешней моделью дороже, чем ответить самому.

## 2. Проблема

Домашнее задание и автопроверка задач перестали быть сигналом. Отраслевые отчёты 2026 года дают порядка **38 % кандидатов с признаками ИИ-подсказки в отборе**, а в разработке — около половины. Результат генерируется за три секунды, и «зелёные тесты» доказывают только то, что у человека есть доступ к ассистенту.

Существующие ответы рынка бьют мимо:

- **Автопроверка задач** (HackerRank, CodeSignal, Яндекс Контест) проверяет результат, а результат генерируется.
- **Прокторинг** (Экзамус, ProctorEdu) проверяет поведение: камера, экран, биометрия. Это ловит списывание, но не отвечает на вопрос «понимает ли человек то, что написал», требует согласий на обработку биометрии и неприменимо в закрытом контуре.
- **Живой техсобес** отвечает на вопрос правильно, но стоит 2–4 часа времени senior-инженера и не воспроизводится при споре.

ПРУФ проверяет **авторство понимания**, а не поведение и не результат.

## 3. Продукт целиком

### 3.1. Кандидат

1. Получает ссылку на проверку (или заходит сам — бесплатно).
2. Пишет или загружает решение прямо в браузере, в редакторе с подсветкой.
3. Жмёт «Проверить» — платформа строит мутации и прогоняет тесты.
4. Проходит сессию защиты: 15 минут, 6–15 вопросов по конкретным строкам.
5. Получает протокол понимания в PDF. Протокол остаётся **у кандидата** и переиспользуется в других компаниях.

### 3.2. Работодатель

1. Заводит вакансию и задание.
2. Отправляет кандидатам ссылку на проверку.
3. Видит пул кандидатов: контроль кода в процентах, риски, статус.
4. Открывает карточку: шкала контроля, цитаты мутаций, таймлайн защиты, дыры в тестах.
5. Сравнивает двух кандидатов построчно, ставит решение (пригласить / отклонить / на разбор), выгружает CSV, скачивает PDF.

### 3.3. Вуз / СПО

Бесплатный трек. Запуск из Moodle по LTI 1.3, оценка обратно в журнал. Преподаватель получает то, чего у него нет: подтверждение, что студент понимает сданный код.

**Принципы, заложенные в архитектуру:**

- **Ноль внешних зависимостей в рантайме.** Только стандартная библиотека Python (reportlab опционален — без него PDF деградирует в текст). Это условие для on-premise в закрытом контуре.
- **Ядро не знает про HTTP.** `engine/` можно вызвать из CLI, из сервера, из чужого пайплайна.
- **Фронтенд без сборки.** Никакого npm, бандлеров и CDN: открывается с файловой системы, работает офлайн.

## 5. Ядро: генератор мутаций

**Задача:** из одного решения получить 9–15 осмысленных правок, каждая из которых меняет поведение программы, но не ломает синтаксис.

### 5.1. Конвейер

1. **Парсинг.** `ast.parse` даёт дерево с точными координатами узлов.
2. **Поиск точек мутации.** Обход дерева, каждый оператор сообщает, применим ли он к узлу. Точка = (узел, оператор, предполагаемая замена).
3. **Побайтовая склейка.** Замена делается **не через `ast.unparse`**, а вырезанием байтового диапазона исходника по `lineno/col_offset` с поправкой на UTF-8. Причина: `unparse` переписывает весь файл, ломает форматирование и комментарии, и кандидат не узнаёт свой код. Наш подход меняет ровно один фрагмент — диff всегда в одну-две строки.
4. **Проверка компиляции.** Каждый мутант компилируется `compile()`. Невалидное отбрасывается.
5. **Дедупликация.** SHA-256 по тексту мутанта: одинаковые правки из разных операторов схлопываются.
6. **Диверсификация.** Round-robin по операторам и по навыкам, чтобы 12 мутаций не оказались двенадцатью сдвигами границ в одном цикле.
7. **Нумерация.** `M01 … M15` в порядке появления в коде.

### 5.2. Константы

| Константа | Значение | Смысл |
| --- | --- | --- |
| `DEFAULT_LIMIT` | 12 | Сколько мутаций строим по умолчанию |
| `MAX_LIMIT` | 15 | Потолок: больше не помещается в 15 минут |
| `MIN_USEFUL` | 3 | Меньше — сессия бессмысленна, платформа откажет |

### 5.3. Отпечаток кода

`code_fingerprint(code)` — SHA-256 от нормализованного исходника, первые 16 hex-символов. Отпечаток печатается в протоколе. Любой спор разбирается так: берём отпечаток, перегенерируем мутации, получаем тот же набор.

Пример из демо-задания: `392829790817d1b8`.

## 6. Каталог из 18 операторов

| # | Код | Что делает | Навык |
| --- | --- | --- | --- |
| 1 | `CMP_BOUNDARY` | `<` ↔ `<=`, `>` ↔ `>=` | boundary |
| 2 | `CMP_EQUALITY` | `==` ↔ `!=` | logic |
| 3 | `CMP_MEMBERSHIP` | `in` ↔ `not in` | collections |
| 4 | `CMP_IDENTITY` | `is` ↔ `is not` | logic |
| 5 | `BOOL_OP` | `and` ↔ `or` | logic |
| 6 | `NOT_DROP` | Убирает `not` | logic |
| 7 | `ARITH_OP` | `+` ↔ `-`, `*` ↔ `/` | arithmetic |
| 8 | `DIV_KIND` | `/` ↔ `//` | arithmetic |
| 9 | `AUG_OP` | `+=` ↔ `-=` и т. п. | arithmetic |
| 10 | `CONST_INT` | `n` → `n ± 1`, `0` → `1` | boundary |
| 11 | `CONST_BOOL` | `True` ↔ `False` | logic |
| 12 | `CONST_STR_IO` | Меняет строковый литерал разделителя/формата | strings |
| 13 | `CALL_DROP_METHOD` | Убирает вызов метода: `s.strip()` → `s` | strings |
| 14 | `CALL_SWAP_METHOD` | `strip` ↔ `lstrip`, `upper` ↔ `lower`, `split` ↔ `rsplit` | strings |
| 15 | `SLICE_SHIFT` | Сдвигает границу среза на 1 | boundary |
| 16 | `RANGE_BOUND` | Сдвигает границу `range` | boundary |
| 17 | `EXCEPT_SWALLOW` | Тело `except` заменяется на `pass` | errors |
| 18 | `RETURN_DROP` | Убирает `return`, функция возвращает `None` | flow |

Каталог доступен программно: `GET /api/catalog` и `python3 -m engine.cli catalog`.

**Почему именно эти 18.** Каждый оператор отобран по критерию «правка правдоподобна как человеческая ошибка и её легко не заметить глазами». Операторы, которые ломают код очевидно (удаление целого блока, переименование переменной), исключены: они не различают понимание.

## 7. Песочница выполнения

Запуск чужого кода — главный риск платформы. Изоляция построена слоями.

| Слой | Как сделано |
| --- | --- |
| Процесс | Отдельный процесс `python -I -S`: игнорируются пользовательские пути, не подхватывается `site` |
| Файловая система | Временный каталог на запуск, удаляется после прогона |
| Окружение | Чистый `env`, `PYTHONHASHSEED=0` |
| Время | `DEFAULT_TIMEOUT = 10.0` с на прогон, `RLIMIT_CPU = 5` с |
| Память | `RLIMIT_AS = 512 МБ` |
| Запись на диск | `RLIMIT_FSIZE` |
| Импорты | Блок-лист опасных модулей (сеть, процессы, системные вызовы) |
| Размер кода | `MAX_CODE_BYTES = 200 000` |
| Канал результата | Одна строка JSON после маркера `__PRUF__`. Всё остальное в stdout — шум пользователя, он не может подделать результат |
| Кэш | SHA-256 от (код + тесты + лимиты), `CACHE_LIMIT = 512` записей. Прогон 12 мутантов одного решения не повторяет одинаковую работу |

Функции: `run_tests(code, tests, ...)` — один прогон; `run_many(...)` — пакет мутантов с общим кэшем.

**Ограничение честно:** это изоляция уровня процесса, а не контейнера. Для продакшена слой заворачивается в контейнер с seccomp-профилем и сетевой политикой deny-all; интерфейс `sandbox.py` при этом не меняется.

## 8. Анализ решения

`analysis.analyze(code, tests, limit)` возвращает единый отчёт:

- `syntax_check` — синтаксис решения и тестов до любых прогонов;
- `preview` — список мутаций с диффами, без прогона (быстрый путь для студии);
- прогон базовых тестов на оригинале: если оригинал красный, дальше идти нельзя;
- прогон каждого мутанта: **killed** (тесты заметили) или **survived** (прошёл незамеченным);
- `mutation_score_pct` = killed / total × 100;
- `verdict_for(score, survived)` — вердикт по набору тестов.

### 8.1. Что значит выживший мутант

Выживший мутант — **дыра в наборе тестов**. Это ценнее, чем зелёный прогон: он показывает, какое поведение никто не проверяет. Именно выжившие мутанты дают самые сильные вопросы защиты («ни один тест не заметит эту правку — почему?»).

### 8.2. Демонстрационный прогон

`python3 -m engine.cli demo` на эталонном задании «Разбор заказов из текстового файла»:

| Показатель | Значение |
| --- | --- |
| Мутаций построено | 12 |
| Тесты поймали (killed) | 7 |
| Прошли незамеченными (survived) | 5 |
| Mutation score | 58 % |
| Вопросов в сессии | 13 |
| Верных ответов | 9 |
| Контроль кода | 70 % |
| Отпечаток | `392829790817d1b8` |

Все числа воспроизводятся повторным запуском той же команды.

## 9. Сессия защиты: алгоритм 15 минут

### 9.1. Константы

| Константа | Значение |
| --- | --- |
| `SESSION_SECONDS` | 900 (15 минут) |
| `MIN_QUESTIONS` | 6 |
| `MAX_QUESTIONS` | 15 |
| `DEFAULT_QUESTIONS` | 13 |
| `MAX_PER_MUTATION` | 2 |

### 9.2. Четыре типа вопросов

| Тип | Формулировка | Вес |
| --- | --- | --- |
| `danger` | «Какая из трёх правок опасна?» — три диффа на выбор | 1.2 |
| `gap` | «Какой тест поймает эту правку?» — включая вариант «ни один тест не заметит правку» | 1.3 |
| `first_failure` | «Какой тест упадёт первым?» | 1.0 |
| `consequence` | «Что произойдёт при таком входе?» | 1.0 |

В каждом вопросе с закрытыми вариантами присутствуют две специальные опции:

- `NO_TEST_OPTION` = «Ни один тест не заметит правку» — правильный ответ для выживших мутантов;
- `CRASH_OPTION` = «Прогон упадёт целиком: ошибка или таймаут».

Без них кандидат угадывает методом исключения; с ними — обязан рассуждать.

### 9.3. Сборка набора вопросов

1. Мутации сортируются по информативности: выжившие вперёд, затем killed с редкими навыками.
2. С одной мутации берётся максимум 2 вопроса — иначе сессия превращается в допрос про одну строку.
3. Набор добивается до 13 вопросов (или меньше, если мутаций мало, но не меньше 6).
4. Порядок вариантов перемешивается **детерминированно**: `random.Random(sha256(fingerprint + session_id + type + mutation_id))`. Тот же кандидат на том же коде получит тот же порядок; другой кандидат — другой.

### 9.4. Ход сессии

- Таймер 900 секунд, обратный отсчёт на кольцевой шкале; последние 2 минуты — красный.
- Каждый ответ фиксируется с временем в секундах — это попадёт в таймлайн протокола.
- Можно завершить досрочно: «Завершить» → сборка протокола по отвеченным вопросам.
- По истечении таймера сессия закрывается автоматически, неотвеченные считаются неверными.
- `public_view()` отдаёт клиенту вопросы **без поля `correct`**. Правильные ответы не покидают сервер до завершения.

## 10. Протокол понимания

Протокол — главный артефакт продукта. Не оценка, а разбор.

### 10.1. Структура

| Поле | Содержание |
| --- | --- |
| `id`, `session_id`, `created_at` | Идентификация |
| `fingerprint` | Отпечаток кода — ключ к воспроизведению |
| `candidate`, `task` | Кто и что решал |
| `control_pct` | Контроль кода в процентах — главное число |
| `passed`, `pass_threshold_pct` | Пройден ли порог (по умолчанию 70 %) |
| `verdict` | `{level, label, summary, tests_note}` |
| `mutation` | `{total, killed, survived, score_pct, verdict}` |
| `questions` | Все вопросы с ответами кандидата и верными |
| `skills` | Карта навыков (раздел 11) |
| `risks` | Зоны риска: дыры в тестах, неконтролируемые навыки |
| `quotes` | Цитаты мутаций: строка, дифф, вопрос |
| `timeline` | Хронология: что спросили, что ответил, за сколько секунд |
| `duration_seconds`, `duration_clock` | Длительность |
| `engine`, `reproducible` | Версия ядра и команда для воспроизведения |

### 10.2. Градация

| Порог | Константа | Значение |
| --- | --- | --- |
| Контролирует | `SKILL_CONTROL` | ≥ 0,80 |
| Шатко | `SKILL_SHAKY` | ≥ 0,50 |
| Не контролирует | — | < 0,50 |
| Порог допуска | `PASS_CONTROL_PCT` | 70 % |

Порог 70 % — не абсолютная истина, а настройка компании. В кабинете работодателя он меняется в «Настройках» и печатается в протоколе, чтобы вердикт нельзя было трактовать задним числом.

### 10.3. Форматы выдачи

- **PDF** — `render_pdf(protocol, path=None)`. При `path=None` возвращает байты (для отдачи по HTTP), иначе пишет файл. Кириллический шрифт ищется по списку кандидатов; если ни одного нет, включается безопасный fallback.
- **Текст** — `render_text(protocol)`, тот же разбор в plain text. Нужен для закрытого контура, где PDF-вьюеры ограничены, и для дифференциального сравнения протоколов.

| Ось | Что проверяет |

## 12. HTTP API

Базовый префикс `/api`. Формат ошибок: `{"ok": false, "error": "текст", "status": код}`. Лимит тела запроса `MAX_BODY = 400 000` байт.

### 12.1. GET

| Маршрут | Ответ |
| --- | --- |
| `/api/health` | Состояние сервиса, версия, число операторов, офлайн-флаг |
| `/api/catalog` | 18 операторов с описаниями и навыками |
| `/api/tasks` | Демо-задания (`orders`, `words`, `phone`) |
| `/api/vacancies` | Вакансии демо-компании |
| `/api/candidates` | Пул кандидатов со сводкой |
| `/api/candidates/<id>` | Полный бандл: кандидат, сводка, протокол, анализ, код, тесты |
| `/api/protocol/<id>` | Протокол в JSON |
| `/api/protocol/<id>.pdf` | Протокол в PDF |
| `/api/protocol/<id>.txt` | Протокол в тексте |
| `/api/session/<id>` | Публичное состояние сессии (без правильных ответов) |
| `/api/economics` | Юнит-экономика и безубыточность |
| `/api/demo` | Полный демо-прогон одним запросом |
| `/api/leads` | Заявки с лендинга |

### 12.2. POST

| Маршрут | Тело | Что делает |
| --- | --- | --- |
| `/api/mutations` | `{code, limit}` | Превью мутаций без прогона |
| `/api/run` | `{code, tests}` | Прогон тестов в песочнице |
| `/api/analyze` | `{code, tests, limit}` | Полный анализ: мутации + прогон + score |
| `/api/session/start` | `{code, tests, candidate, task}` | Создаёт сессию защиты |
| `/api/session/<id>/answer` | `{question, answer}` | Принимает ответ |
| `/api/session/<id>/finish` | — | Завершает и собирает протокол |
| `/api/protocol/<id>/send` | `{email}` | Ставит протокол в очередь отправки (`data/outbox`) |

## 14. Веб-интерфейс

### 14.1. Лендинг (`index.html`)

Тёмная навигационная палитра, малиновый и мятный акценты. WebGL-сцена с плавающими стеклянными объёмами и параллаксом, анимация появления блоков при скролле, счётчики. Сцена деградирует корректно: при отсутствии WebGL остаётся статичный градиент, вёрстка не ломается.

### 14.2. Студия (`studio.html`)

Три колонки: редактор решения, список мутаций `M1…M13` со статусами, вопрос с разбором и консоль прогона тестов. Здесь **действительно можно писать свой код**: он уходит в `/api/analyze`, мутации строятся из него, тесты гоняются в песочнице. Слева — степпер из пяти шагов, сверху — таймер сессии.

### 14.3. Защита (`session.html`)

Кольцевой таймер 15:00 (красный на последних двух минутах), счётчик «Вопрос N из M», read-only код с бейджем мутации и парой «было → стало», три варианта-диффа, панель разбора справа, состояния «готово / пауза / завершено» и переход «Смотреть протокол».

### 14.4. Кабинет работодателя (`employer.html`)

Сайдбар с вакансиями и фильтрами по статусу, KPI-строка, таблица кандидатов с полосами контроля и красными чипами рисков, панель детали со шкалой контроля, цитатами мутаций и таймлайном, сравнение двух кандидатов, экспорт CSV, решения по кандидату.

### 14.5. Кабинет кандидата (`candidate.html`)

Список протоколов, карта навыков, зоны риска, таймлайн защиты, шкала контроля, PDF/текст, ссылка для работодателя, управление приватностью («забыть сессии»).

## 15. Модель данных

Хранилище — файловое, JSON, каталог `data/`:

| Коллекция | Содержимое |
| --- | --- |
| `sessions/` | Сессии защиты |
| `protocols/` | Собранные протоколы |

| `outbox/` | Очередь отправки протоколов (в прототипе почта не уходит) |

Файловое хранилище выбрано осознанно: в закрытом контуре развернуть PostgreSQL — отдельный проект с согласованиями. Интерфейс `store.py` изолирован, замена на СУБД — одна реализация модуля.

## 16. Детерминизм и воспроизводимость

Это главное коммерческое свойство, поэтому оно вынесено в отдельный раздел.

| Источник недетерминизма | Как убран |
| --- | --- |
| Порядок обхода AST | Фиксированный обход, стабильная сортировка точек |
| Хеши строк Python | `PYTHONHASHSEED=0` в песочнице |
| Перемешивание вариантов | Сид из SHA-256(отпечаток + сессия + тип + мутация) |
| Время прогона | Не участвует в вердикте, только в таймлайне |
| Кэш прогонов | Ключ — SHA-256 содержимого, не время |
| Версия ядра | Пишется в протокол (`pruf.engine/1`) |

В каждом протоколе есть поле `reproducible` с точной командой, которая повторяет результат. Апелляция кандидата разбирается не спором, а прогоном.

## 17. Безопасность

- Код кандидата исполняется **только** в песочнице (раздел 7), никогда в процессе сервера.
- Правильные ответы не отдаются клиенту до завершения сессии.
- Лимит тела запроса 400 КБ, лимит кода 200 КБ.
- Никаких исходящих сетевых вызовов из ядра: платформа работает при полностью отключённой сети. Это проверяется офлайн-демо.
- Нет вызовов LLM — ни в генерации мутаций, ни в вопросах, ни в вердикте. Следовательно, нет утечки кода кандидата во внешние модели.

---

## 18. Приватность

- **Без прокторинга.** Ни камеры, ни записи экрана, ни биометрии. Проверяется содержание, а не поведение. Это снимает целый пласт согласий на обработку биометрических данных и делает продукт применимым там, где прокторинг запрещён политикой.
- **Протокол принадлежит кандидату.** Он видит его целиком, может скачать и переиспользовать в других компаниях. Работодатель получает копию, а не единственный экземпляр.
- **Кнопка «забыть сессии».** Локальные черновики и история сессий удаляются по запросу кандидата.
- **Минимум данных.** Для проверки нужны имя и код. Ни паспорта, ни селфи, ни телефона.

На лендинге те же линии в публичной упаковке: кандидат — бесплатно, вуз — от 290 ₽/мес, работодатель — от 990 ₽.

### 19.2. Себестоимость

Переменная себестоимость сессии — процессорное время контейнера, единицы копеек. Сюда же относится сравнение **0 ₽ за защиту против 10,14 ₽ у LLM-подхода**: это аргумент **себестоимости и маржи**, а не ценности для покупателя. В питче и на лендинге он живёт только в разделе про издержки — покупателю экономия 10 ₽ не интересна, ему интересны часы senior-инженера.

### 19.3. Безубыточность

При постоянных затратах уровня гранта (≈ 1,2 млн ₽ в год) точка безубыточности — **800–900 верификаций в год**, то есть **3–5 активных компаний**. Для сравнения: в предыдущей вузовской модели ноль достигался на 3 745 студентах, это 2–3 вуза одновременно — недостижимо для команды из четырёх человек без отдела продаж.

Сценарии выручки по «12 вузам и 20 000 студентов» из документации Стапеля **исключены сознательно**: ни одного подписанного пилота нет, и на защите это проверят первым вопросом.

## 20. Кто платит в первый год

Отдельный раздел, потому что это первый вопрос жюри и первый вопрос инвестора.

| Сегмент | Целевая компания для пилота | Почему заплатит | Чек |
| --- | --- | --- | --- |
| ИТ-компания 50–500 человек, массовый найм junior/middle | Продуктовая компания с потоком тестовых заданий (например, региональный офис крупного интегратора) | Поток резюме вырос, доля ИИ-подсказки ~38 %, senior-инженеры тратят 2–4 часа на кандидата | 90 000–150 000 ₽ за пакет 100 верификаций |
| Компания со стажировками и целевым набором | Компания, набирающая 30–100 стажёров в год | Реальный уровень стажёра виден на третий месяц; нужна карта пробелов до выхода на проект | 150 000–250 000 ₽ подписка |
| Предприятие закрытого контура (ОПК, судостроение, БПЛА) | Предприятие с запретом облачных сервисов и внешних LLM | Облачные тренажёры запрещены, а допускать людей к работам надо | 400 000–900 000 ₽ on-premise |

Три пилота этого профиля закрывают точку безубыточности. Конкретные юрлица указываются в заявке; здесь зафиксирован профиль, чтобы документ не устаревал при смене переговоров.

**Срок сделки:** договор на пилот с ИТ-компанией подписывается за две недели. В вузовской модели путь «понравилось кафедре → платёж» занимал учебный год, часто два.

## 22. Вузовский трек и Moodle

Позиция формулируется одной фразой: **мы не заменяем Moodle, мы закрываем дыру, которую Moodle закрыть не может — он не умеет отличить понимание от сданного задания.**

| Было в Стапеле | Стало в ПРУФ |
| --- | --- |
| «Платформа микрообучения для вуза» | «Модуль защиты понимания», запускаемый из курса |
| Отдельный вход, отдельные экраны, отдельная ведомость | Запуск по **LTI 1.3 Advantage** из курса Moodle |
| Отдельная ведомость | Оценка уходит обратно в журнал курса через **AGS** |
| Ручные списки групп | Состав группы подтягивается через **NRPS** |
| Вуз платит 190 ₽ за студента | Вуз не платит ничего |
| Продажа через закупку | Внедрение через приказ по кафедре — это не закупка |

Отдельно учтено: с 2025 года на «цифровые кафедры» берут студентов не-ИТ направлений. Вузовский трек целится именно туда — гуманитарии и инженеры, которых учат программировать с нуля.

Из вузовского трека сохраняются как бесплатная приманка: валидатор курса C01–C12 и отчёт по индикаторам ФГОС.

| BKT + Elo + кривая забывания | Переиспользуется как «карта пробелов» сотрудника вместо рекомендаций студенту |
| Валидатор курса C01–C12 | Остаётся в вузовском бесплатном треке |
| Лиги, дуэли, командный зачёт | Убрано: в B2B это минус, а не плюс |
| Отчёт по индикаторам ФГОС | Остаётся в вузовском треке как бесплатная приманка |

По коду это примерно 70 % сохранения и 30 % переписывания интерфейсов.

Отдельная правка формулировок: показатель, который в документации Стапеля назывался «Точность подбора шага 78 %», переименован в **«целевая вероятность успеха на шаге — 78 %»**. Прежняя формулировка читалась как измеренная точность модели, чего замер не показывал.

## 27. Масштабирование на другие языки

Ядро не знает про Python как про предметную область — оно знает про AST и про операторы. Перенос на новый язык:

1. Парсер языка → дерево с координатами (для JS — любой стандартный парсер, для Java — грамматика компилятора).
2. Отображение 18 операторов на конструкции языка. Часть переносится один в один (`CMP_BOUNDARY`, `BOOL_OP`, `ARITH_OP`), часть требует адаптации (`EXCEPT_SWALLOW`).
3. Там, где полноценный AST недоступен, работают **текстовые шаблоны с обязательной проверкой компиляции**: правка применяется регулярным выражением, мутант компилируется, некомпилируемое отбрасывается. Качество ниже, но механика сохраняется.
4. Песочница получает свой раннер тестов; лимиты и маркер `__PRUF__` общие.

## 28. Тестирование и критерии приёмки

### 28.1. Автотесты

```bash
python3 -m unittest discover -s tests -v
```

Покрытие: каталог операторов, компилируемость мутантов, дедупликация, детерминизм отпечатка, лимиты генератора, изоляция песочницы (таймаут, память, блок-лист импортов), сборка вопросов, градация навыков, пороги, сборка и рендер протокола, юнит-экономика.

### 28.2. Критерии приёмки прототипа

| # | Критерий | Как проверяется |
| --- | --- | --- |
| 1 | Все страницы отдаются | `curl` по шести страницам → 200 |
| 2 | Произвольный код кандидата даёт мутации | Вставить свой код в студию → построены `M01…` |
| 3 | Мутанты компилируются | Автотест на каталоге заданий |
| 4 | Прогон тестов изолирован | Автотест: бесконечный цикл → таймаут, а не зависание |
| 5 | Сессия ограничена 15 минутами | Таймер и серверная проверка |
| 6 | Правильные ответы не утекают | `public_view()` без поля `correct` |
| 7 | Протокол воспроизводим | Повторный прогон даёт тот же отпечаток и тот же набор |
| 8 | PDF и текст генерируются | `/api/protocol/<id>.pdf` → валидный PDF |
| 9 | Работает офлайн | Отключить сеть, повторить демо |
| 10 | Все кнопки интерфейса имеют обработчик | Сквозной клик-проход по страницам |

## 29. Запуск локально

```bash
git clone https://github.com/akekosik/pruf-platform.git
cd pruf-platform

# проверка ядра без сервера
python3 -m engine.cli catalog
python3 -m engine.cli demo

```

Требования: Python 3.10+. Внешних зависимостей нет. `reportlab` опционален и нужен только для PDF; без него протокол доступен в текстовом виде.

## 30. Словарь

| Термин | Значение |
| --- | --- |
| **Мутация** | Точечная правка исходного кода, меняющая поведение, но не синтаксис |
| **Killed** | Мутация, которую поймал хотя бы один тест |
| **Survived** | Мутация, прошедшая незамеченной — дыра в наборе тестов |
| **Mutation score** | Доля пойманных мутаций, killed / total |
| **Контроль кода** | Взвешенная доля верных ответов на защите, главное число протокола |
| **Отпечаток** | SHA-256 нормализованного кода, 16 hex-символов; ключ воспроизведения |
| **Протокол понимания** | Итоговый документ: разбор по строкам, навыкам и рискам |
| **Защита** | 15-минутная сессия вопросов по собственному коду |
| **Зона риска** | Дыра в тестах или неконтролируемый навык, попавший в протокол |
| **Закрытый контур** | Сеть без доступа в интернет; требует on-premise и работы без LLM |
